# Plan: Build the Analytics Page

## Goal

Replace the placeholder `client/src/pages/Analytics.tsx` with a fully designed analytics dashboard that matches the visual language of the existing protected pages and uses the current analytics APIs.

## Current State

- `client/src/pages/Analytics.tsx` is only a placeholder.
- The protected app already uses the shared sidebar layout via `client/src/components/common/Layout.tsx`.
- The project already has `recharts` installed in `client/package.json`, but no page is using it yet.
- Client analytics data access already exists in `client/src/services/analyticsService.ts`.
- Backend analytics endpoints already exist and return usable data:
  - `GET /analytics/summary`
  - `GET /analytics/mood-trends`
  - `GET /analytics/energy-patterns`
  - `GET /analytics/activity-heatmap`
  - `GET /analytics/weekly-report`

## Design Direction

Follow the design system already established by `Home`, `SelfCare`, and `EmotionalGuidance`, not the standalone `review.html` top-nav pattern.

Key cues to reuse:

- Soft sage/sand/clay palette on a light page background
- Large serif display headings with `font-display`
- White cards with `rounded-[1.75rem]`, subtle borders, and `shadow-soft`
- One prominent hero/intro section at the top
- Dense but breathable dashboard spacing with 2-column or 3-column responsive grids
- Calm, wellness-oriented copy instead of generic analytics language

## Proposed Page Structure

1. Hero summary section
   - Large title like `Your Wellness Analytics`
   - Short supporting copy explaining the page
   - Period filter control (`7days`, `30days`, `90days`, `year`)
   - One small insight badge or calming tagline to match the tone of the other pages

2. Summary metric cards
   - `Current Streak`
   - `Average Mood`
   - `Average Water Intake`
   - `Average Sleep`
   - `Completion Rate`
   - These should visually match the stat-card treatment used in `WellnessOverview.tsx`

3. Main analytics grid
   - Left: mood trend chart for the selected period
   - Right: weekly report / top feelings / quick takeaways card

4. Secondary analytics grid
   - Energy pattern chart by hour of day
   - Activity heatmap for the selected year

5. Insight footer / empty-state support
   - If data is sparse, show a styled encouragement card instead of empty visual space
   - Keep the page useful even for first-time users

## Chart and Data Mapping Plan

### 1. Summary cards

Source: `analyticsService.getSummary(period)`

Expected payload:

- `totalEntries`
- `currentStreak`
- `averageMood`
- `averageWaterIntake`
- `averageSleepHours`
- `completionRate`

Display rules:

- Convert numeric mood into a user-friendly label or paired numeric display, for example `3.8 / 5` plus a qualitative label.
- Format water and sleep with units.
- Show `0` values as valid data, not as missing state.

### 2. Mood trends chart

Source: `analyticsService.getMoodTrends(period)`

Expected shape:

- `{ date, mood }[]`

Implementation notes:

- Use a `ResponsiveContainer` with an `AreaChart` or `LineChart`.
- Format dates for the x-axis based on selected period.
- Keep y-axis bounded to the app's mood scale.
- Use the sage/green accent already used elsewhere, with a soft gradient fill.

### 3. Energy patterns chart

Source: `analyticsService.getEnergyPatterns()`

Expected shape:

- `{ hour, averageEnergy }[]`

Implementation notes:

- Use a `LineChart` or slim `BarChart`.
- Format hour labels into readable times such as `6 AM`, `9 AM`, `12 PM`.
- Surface the strongest window as a plain-language insight if easy to derive.

### 4. Activity heatmap

Source: `analyticsService.getActivityHeatmap(year)`

Expected shape:

- `{ date, completionRate }[]`

Implementation notes:

- Build a custom heatmap grid in JSX/CSS rather than bringing in another chart dependency.
- Group by week/day similar to contribution heatmaps.
- Use 4-5 intensity levels derived from `completionRate`.
- Include month markers if they fit cleanly; otherwise prioritize a readable mobile-safe layout.

### 5. Weekly report card

Source: `analyticsService.getWeeklyReport()`

Expected payload:

- `daysLogged`
- `averageMood`
- `averageWaterIntake`
- `averageSleepHours`
- `topFeelings`

Implementation notes:

- Present this as a high-polish summary card rather than a raw JSON-style stat block.
- Use pills or small badges for `topFeelings`.
- Add one or two derived insight sentences if the data allows.

## State and Interaction Plan

- Add local state for:
  - `period`
  - `year`
  - `loading`
  - `error`
  - fetched datasets
- Fetch summary and mood trends whenever `period` changes.
- Fetch activity heatmap whenever `year` changes.
- Fetch energy patterns and weekly report on initial load.
- Use a single coordinated loading experience so the page does not pop in card-by-card.
- Show graceful empty states inside cards when datasets are empty.

## Styling Plan

- Keep most layout styling in Tailwind classes inside `Analytics.tsx`.
- Add a dedicated page CSS file only if needed for:
  - heatmap grid sizing
  - custom legend styles
  - chart container polish not convenient in utility classes
- Match existing spacing conventions:
  - top hero block
  - `gap-6` / `gap-8` between sections
  - `max-w-[1200px]` or shared layout width behavior

## Implementation Steps

1. Replace the analytics placeholder with a full page shell consistent with the protected dashboard design.
2. Add typed local interfaces for the analytics responses inside `Analytics.tsx` or a nearby shared type block.
3. Wire the page to `analyticsService` and fetch all required datasets.
4. Build the hero section and summary stat cards.
5. Add the mood trends chart using `recharts`.
6. Add the energy pattern chart using `recharts`.
7. Build the custom yearly heatmap component directly in the page.
8. Add the weekly report and top-feelings insight card.
9. Add loading, empty, and error states that still match the visual system.
10. Refine responsive layout so desktop feels dashboard-like and mobile stacks cleanly.

## Files Expected To Change

- `client/src/pages/Analytics.tsx`
- Possibly `client/src/styles/pages/analytics.css` if the heatmap or chart polish needs dedicated CSS

## Verification

- Run `npm -C client run build`.
- Manually verify `/analytics` on desktop and mobile widths.
- Confirm period switching updates summary + mood data.
- Confirm year switching updates the heatmap.
- Confirm cards handle empty API responses without breaking layout.
- Confirm typography, card radii, shadows, and spacing visually align with `Home`, `SelfCare`, and `EmotionalGuidance`.

## Assumptions

- No backend changes are needed because the required analytics endpoints already exist.
- The analytics page should live inside the existing sidebar layout, not introduce another page-specific navigation shell.
- The first implementation should prioritize design consistency and correctness over adding extra filters beyond `period` and `year`.

# Plan: Build the Settings Page

## Goal

Replace the placeholder `client/src/pages/Settings.tsx` with a fully designed settings experience that matches the protected-page design system and exposes the account controls already supported by the backend.

## Current State

- `client/src/pages/Settings.tsx` is only a placeholder.
- The protected app already uses the shared sidebar layout via `client/src/components/common/Layout.tsx` and `client/src/components/common/Sidebar.tsx`.
- The client auth layer already supports:
  - `authService.updateProfile(data)`
  - `authService.updatePassword(data)`
  - `AuthContext.updateProfile(data)`
- The backend already supports settings-relevant endpoints:
  - `PUT /auth/profile`
  - `PUT /auth/password`
  - `GET /users/preferences`
  - `PUT /users/preferences`
  - `GET /users/export`
  - `DELETE /users/account`
- The user model already defines preferences for:
  - `theme`
  - `notifications.dailyReminder`
  - `notifications.reminderTime`
  - `notifications.weeklyReport`
  - `privacy.shareStats`

## Design Direction

Follow the same visual system used across `Home`, `EmotionalGuidance`, `SelfCare`, and the new analytics page.

Key cues to reuse:

- Soft wellness palette with sage-led accents
- Serif hero headings with `font-display`
- Rounded white cards with subtle borders and `shadow-soft`
- Clean section grouping rather than a dense generic settings form
- Calm, supportive copy that feels reflective instead of sterile

The settings page should feel like a personal account sanctuary, not a generic admin console.

## Proposed Page Structure

1. Hero / account overview section
   - Heading like `Your Settings` or `Account & Preferences`
   - Short supporting copy
   - Compact identity card showing user name, email, avatar, and one short status line

2. Main two-column layout on desktop
   - Left column:
     - Profile details card
     - Preferences card
     - Password card
   - Right column:
     - Account snapshot / guidance card
     - Data export card
     - Danger zone card for delete account

3. Mobile layout
   - Stack sections vertically in the same visual order
   - Keep destructive actions isolated and clearly separated at the bottom

## Settings Sections Plan

### 1. Profile Details

Purpose:

- Let the user update visible identity information already supported by `PUT /auth/profile`

Fields:

- `name`
- `avatar` URL or avatar image input placeholder if the existing app uses URLs only
- Read-only email display unless backend email updates are explicitly supported later

Implementation notes:

- Initialize from `useAuth().user`
- Save via `updateProfile({ name, avatar })`
- Keep this card visually prominent because it is the most personal part of settings

### 2. Preferences

Purpose:

- Surface the preferences already present in `User.preferences`

Controls:

- Theme selector: `light | dark | auto`
- Daily reminder toggle
- Reminder time input
- Weekly report toggle
- Share stats toggle

Data source:

- Read from `user.preferences` initially
- Optionally refresh from `GET /users/preferences` on page load if the implementation wants the freshest server copy
- Save via `PUT /users/preferences`

Implementation notes:

- Group these as calm toggle rows and segmented selectors rather than raw stacked checkboxes
- If `dailyReminder` is off, the reminder time can be visually de-emphasized or disabled

### 3. Password Update

Purpose:

- Allow users to change their password through the existing auth endpoint

Fields:

- `currentPassword`
- `newPassword`
- `confirmNewPassword`

Implementation notes:

- Validate confirm password on the client before submitting
- Submit via `authService.updatePassword`
- Keep the form visually self-contained with a clear save button and short helper copy

### 4. Data Export

Purpose:

- Give users access to the existing `GET /users/export` data export capability

Implementation notes:

- Present this as a dedicated card with a short explanation of what will be included
- Trigger browser download from the API response
- Keep the action secondary, not primary

### 5. Delete Account

Purpose:

- Expose the existing `DELETE /users/account` endpoint safely

Implementation notes:

- Place this in a clearly separated danger zone card
- Require an explicit confirmation step in the UI before deletion
- After success, clear auth state and redirect to login or landing flow
- Use strong warning copy because this is irreversible

## State and Interaction Plan

- Add local state for:
  - profile form values
  - preferences values
  - password form values
  - per-section saving/loading flags
  - export state
  - delete confirmation state
- Prefer section-level save actions rather than one global save button
- Keep one success/error feedback path per section so failures do not block unrelated changes
- Rehydrate local state from `useAuth().user` when user data becomes available

## API and Service Plan

Existing service support:

- `authService.updateProfile`
- `authService.updatePassword`

Likely additions needed on the client side:

- A small `userService` or page-local API helpers for:
  - `getPreferences`
  - `updatePreferences`
  - `exportData`
  - `deleteAccount`

Minimal-change path:

- If the team prefers fewer files, page-local helpers inside `Settings.tsx` can call `api` directly
- If consistency with other domains matters more, add a dedicated `client/src/services/userService.ts`

Recommended direction:

- Add `userService.ts` so settings-related account actions are not split awkwardly between the page and `authService`

## UX and Validation Plan

- Profile:
  - Require non-empty name
  - Keep avatar optional
- Password:
  - Require current password
  - Require minimum length alignment with backend expectations
  - Require new password confirmation match
- Preferences:
  - Allow immediate editing, explicit save
  - Disable reminder time when daily reminder is off
- Delete account:
  - Require typed confirmation or a modal confirmation step

## Styling Plan

- Keep the page inside the shared sidebar layout
- Use a hero intro card at the top like the other protected pages
- Use a desktop grid such as:
  - `xl:grid-cols-[minmax(0,1.6fr)_minmax(320px,1fr)]`
- Use `rounded-[1.75rem]`, `border-sage-100`, and `shadow-soft` throughout
- Keep inputs visually aligned with the existing form language from login/register but adapted to the dashboard aesthetic
- Add a dedicated `settings.css` only if needed for custom switches, segmented controls, or danger-zone polish

## Implementation Steps

1. Replace the settings placeholder with a full page shell that matches the protected dashboard pages.
2. Read the authenticated user from `useAuth()` and initialize the profile and preference forms.
3. Add or wire client API helpers for preferences, export, and account deletion.
4. Build the hero/account overview block.
5. Build the profile details card and connect save behavior to `updateProfile`.
6. Build the preferences card and connect save behavior to user preference endpoints.
7. Build the password form and connect save behavior to `authService.updatePassword`.
8. Build the export card and implement download handling.
9. Build the danger zone card with confirmation flow for account deletion.
10. Add loading, success, error, and disabled states so each section behaves independently and predictably.
11. Refine responsive spacing and card balance to match the rest of the protected app.

## Files Expected To Change

- `client/src/pages/Settings.tsx`
- Possibly `client/src/services/userService.ts`
- Possibly `client/src/styles/pages/settings.css`

## Verification

- Run `npm -C client run build`.
- Manually verify `/settings` at desktop and mobile widths.
- Confirm profile updates refresh local user state.
- Confirm preference changes persist correctly.
- Confirm password validation blocks mismatched values before submission.
- Confirm export triggers a valid JSON file download.
- Confirm delete-account flow requires confirmation and handles post-delete logout/redirect correctly.
- Confirm the page visually aligns with `Home`, `EmotionalGuidance`, `SelfCare`, and `Analytics`.

## Assumptions

- Email editing is out of scope for the first implementation because there is no dedicated backend email-update flow shown.
- Backend support already exists for the core settings features, so the main work is UI composition and client wiring.
- The settings page should remain a structured protected-page experience, not a modal or standalone auth-style screen.
