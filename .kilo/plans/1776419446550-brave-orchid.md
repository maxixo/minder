# Plan: Build the Analytics Page

## Goal

Replace the placeholder `client/src/pages/Analytics.tsx` with a fully designed analytics dashboard that matches the visual language of the existing protected pages and uses the current analytics APIs.

## Current State

- `client/src/pages/Analytics.tsx` is only a placeholder.
- The protected app already uses the shared sidebar layout via `client/src/components/common/Layout.tsx`.
- The project already has `recharts` installed in `client/package.json`, but no page is using it yet.
- Client analytics data access already exists in `client/src/services/analyticsService.ts`.
- Backend analytics endpoints already exist and return usable data:
  - `GET /analytics/summary`
  - `GET /analytics/mood-trends`
  - `GET /analytics/energy-patterns`
  - `GET /analytics/activity-heatmap`
  - `GET /analytics/weekly-report`

## Design Direction

Follow the design system already established by `Home`, `SelfCare`, and `EmotionalGuidance`, not the standalone `review.html` top-nav pattern.

Key cues to reuse:

- Soft sage/sand/clay palette on a light page background
- Large serif display headings with `font-display`
- White cards with `rounded-[1.75rem]`, subtle borders, and `shadow-soft`
- One prominent hero/intro section at the top
- Dense but breathable dashboard spacing with 2-column or 3-column responsive grids
- Calm, wellness-oriented copy instead of generic analytics language

## Proposed Page Structure

1. Hero summary section
   - Large title like `Your Wellness Analytics`
   - Short supporting copy explaining the page
   - Period filter control (`7days`, `30days`, `90days`, `year`)
   - One small insight badge or calming tagline to match the tone of the other pages

2. Summary metric cards
   - `Current Streak`
   - `Average Mood`
   - `Average Water Intake`
   - `Average Sleep`
   - `Completion Rate`
   - These should visually match the stat-card treatment used in `WellnessOverview.tsx`

3. Main analytics grid
   - Left: mood trend chart for the selected period
   - Right: weekly report / top feelings / quick takeaways card

4. Secondary analytics grid
   - Energy pattern chart by hour of day
   - Activity heatmap for the selected year

5. Insight footer / empty-state support
   - If data is sparse, show a styled encouragement card instead of empty visual space
   - Keep the page useful even for first-time users

## Chart and Data Mapping Plan

### 1. Summary cards

Source: `analyticsService.getSummary(period)`

Expected payload:

- `totalEntries`
- `currentStreak`
- `averageMood`
- `averageWaterIntake`
- `averageSleepHours`
- `completionRate`

Display rules:

- Convert numeric mood into a user-friendly label or paired numeric display, for example `3.8 / 5` plus a qualitative label.
- Format water and sleep with units.
- Show `0` values as valid data, not as missing state.

### 2. Mood trends chart

Source: `analyticsService.getMoodTrends(period)`

Expected shape:

- `{ date, mood }[]`

Implementation notes:

- Use a `ResponsiveContainer` with an `AreaChart` or `LineChart`.
- Format dates for the x-axis based on selected period.
- Keep y-axis bounded to the app's mood scale.
- Use the sage/green accent already used elsewhere, with a soft gradient fill.

### 3. Energy patterns chart

Source: `analyticsService.getEnergyPatterns()`

Expected shape:

- `{ hour, averageEnergy }[]`

Implementation notes:

- Use a `LineChart` or slim `BarChart`.
- Format hour labels into readable times such as `6 AM`, `9 AM`, `12 PM`.
- Surface the strongest window as a plain-language insight if easy to derive.

### 4. Activity heatmap

Source: `analyticsService.getActivityHeatmap(year)`

Expected shape:

- `{ date, completionRate }[]`

Implementation notes:

- Build a custom heatmap grid in JSX/CSS rather than bringing in another chart dependency.
- Group by week/day similar to contribution heatmaps.
- Use 4-5 intensity levels derived from `completionRate`.
- Include month markers if they fit cleanly; otherwise prioritize a readable mobile-safe layout.

### 5. Weekly report card

Source: `analyticsService.getWeeklyReport()`

Expected payload:

- `daysLogged`
- `averageMood`
- `averageWaterIntake`
- `averageSleepHours`
- `topFeelings`

Implementation notes:

- Present this as a high-polish summary card rather than a raw JSON-style stat block.
- Use pills or small badges for `topFeelings`.
- Add one or two derived insight sentences if the data allows.

## State and Interaction Plan

- Add local state for:
  - `period`
  - `year`
  - `loading`
  - `error`
  - fetched datasets
- Fetch summary and mood trends whenever `period` changes.
- Fetch activity heatmap whenever `year` changes.
- Fetch energy patterns and weekly report on initial load.
- Use a single coordinated loading experience so the page does not pop in card-by-card.
- Show graceful empty states inside cards when datasets are empty.

## Styling Plan

- Keep most layout styling in Tailwind classes inside `Analytics.tsx`.
- Add a dedicated page CSS file only if needed for:
  - heatmap grid sizing
  - custom legend styles
  - chart container polish not convenient in utility classes
- Match existing spacing conventions:
  - top hero block
  - `gap-6` / `gap-8` between sections
  - `max-w-[1200px]` or shared layout width behavior

## Implementation Steps

1. Replace the analytics placeholder with a full page shell consistent with the protected dashboard design.
2. Add typed local interfaces for the analytics responses inside `Analytics.tsx` or a nearby shared type block.
3. Wire the page to `analyticsService` and fetch all required datasets.
4. Build the hero section and summary stat cards.
5. Add the mood trends chart using `recharts`.
6. Add the energy pattern chart using `recharts`.
7. Build the custom yearly heatmap component directly in the page.
8. Add the weekly report and top-feelings insight card.
9. Add loading, empty, and error states that still match the visual system.
10. Refine responsive layout so desktop feels dashboard-like and mobile stacks cleanly.

## Files Expected To Change

- `client/src/pages/Analytics.tsx`
- Possibly `client/src/styles/pages/analytics.css` if the heatmap or chart polish needs dedicated CSS

## Verification

- Run `npm -C client run build`.
- Manually verify `/analytics` on desktop and mobile widths.
- Confirm period switching updates summary + mood data.
- Confirm year switching updates the heatmap.
- Confirm cards handle empty API responses without breaking layout.
- Confirm typography, card radii, shadows, and spacing visually align with `Home`, `SelfCare`, and `EmotionalGuidance`.

## Assumptions

- No backend changes are needed because the required analytics endpoints already exist.
- The analytics page should live inside the existing sidebar layout, not introduce another page-specific navigation shell.
- The first implementation should prioritize design consistency and correctness over adding extra filters beyond `period` and `year`.
